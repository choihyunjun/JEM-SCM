ERP 재고 동기화 · 진단 및 적용 안내

2026-10-19 · ZR700 재고 차이 / 구매입고 5건·고객출고 2건 상세 조회 오류

이 문서는 이전 정책의 진단 기록입니다. 이후 사용자가 ERP 현재고 우선 기준을 확정하여, 이력 오류로 총량 보정을 차단하는 정책과 정수 저장 방식은 변경됐습니다. 최신 적용 방법은 ERP 현재고 기준 재고 보정 안내를 확인하세요.

이번 변경은 오류 기록·진단·실행 제어 개선입니다. 7건의 전표 원인 및 재고 정상화를 완료한 패치는 아닙니다. ERP 원본 응답을 확인하기 전 빈 전표를 정상으로 간주하거나 보정을 강행하지 않습니다. 원재료 kg 수량의 Decimal 전환도 이번 변경에 포함하지 않습니다.

반영 내용

  • API 실패(DETAIL_API_FAILURE), 정상 응답의 빈 상세(DETAIL_EMPTY), 응답 형식 오류(DETAIL_INVALID)를 구분하고 원래 API 오류를 보존합니다.
  • 전체 동기화의 단계별 건수·소요 시간·모든 오류 전표를 StockSyncRun.summary에 저장합니다. 로그의 처음 3건 제한도 제거했습니다.
  • sync_erp_history와 detect_past_changes가 다른 동기화의 잠금에 막히면 traceback 대신 건너뜀으로 종료합니다. 잠금 자체는 유지합니다.
  • sync_erp_auto --days 7은 오늘을 포함한 동일한 7일 범위를 6종 수불에 적용합니다.
  • 기존 전체 동기화 실패는 최근 기간 실행 성공만으로 해제하지 않습니다. 전체 수불과 최종 보정이 모두 성공해야 차단이 해제됩니다. 기존 summary={}의 “수불 오류 N건” 기록도 인식합니다.
  • diagnose_erp_documents는 지정한 전표의 상세 조회만 수행합니다. SCM DB 접근 및 재고 변경은 없으며, API 성공 여부·원래 오류·응답 형태·행 수·품번/수량을 JSON으로 출력합니다.

1. 코드 배포

실행 중인 오래된 cron 프로세스는 새 코드를 재로딩하지 않습니다. 진행 중인 작업이 종료된 뒤 적용·확인합니다. 프로세스 강제 종료나 초기화 옵션은 사용하지 않습니다. 이번 변경에는 모델 변경이나 신규 마이그레이션이 없습니다.

cd /var/www/scm_project && git pull --ff-only origin main && venv/bin/python manage.py check_deployment && sudo systemctl restart gunicorn && sudo systemctl is-active gunicorn

2. 실패 전표 7건 읽기 전용 진단

전체 1년 동기화를 다시 실행할 필요 없이 해당 전표 7건만 조회합니다. 아래 결과로 실제 API 오류인지, 성공했으나 상세가 없는지 구분합니다.

cd /var/www/scm_project && venv/bin/python manage.py diagnose_erp_documents --incoming RV2606000274 RV2607000062 RV2607000153 RV2607000415 RV2608000418 --outgoing IS2601000016 IS2609000372
결과다음 확인
DETAIL_API_FAILUREapi_error에 나온 통신/권한/ERP 오류를 먼저 해결합니다.
DETAIL_EMPTYERP 화면에서 전표의 삭제·취소·상세 품목 유무와 API 계약을 확인합니다. 빈 응답만으로 삭제로 판단하지 않습니다.
DETAIL_INVALID응답 형태 및 API 스키마를 확인합니다.
DETAIL_OK현재 상세 조회는 정상입니다. 이전 일시 오류 또는 다른 실행 시점의 문제인지 확인합니다. 이 진단은 이력 반영이나 보정은 실행하지 않습니다.

2-1. 10월 19일 서버 진단 결과 및 추가 확인

서버 배포 후 DB 점검은 104개 테이블, 미적용 마이그레이션·누락 테이블·누락 컬럼 모두 0으로 통과했습니다. 구매입고 5건 및 고객출고 2건은 모두 api_success=true, response_type=list, row_count=0입니다. 즉, 성공 응답에 상세 행이 없어 보정이 보류됩니다. 전표 삭제·취소나 ZR700과의 직접 관계는 아직 확인되지 않았습니다.

추가된 --context 옵션은 지정 기간의 ERP 전표 목록에서 해당 번호만 추출하고, SCM에 저장된 동일 전표 및 전표-순번 수불을 조회합니다. ERP 조회 구간에서는 DB 접근을 차단하고, SCM 조회 구간에서는 SELECT만 허용합니다. 동기화·삭제·재고 변경은 수행하지 않습니다. 옵션 없이 실행하면 기존처럼 SCM DB에 접근하지 않습니다.

cd /var/www/scm_project && git pull --ff-only origin main && venv/bin/python manage.py diagnose_erp_documents --context --from 20260101 --to 20261019 --incoming RV2606000274 RV2607000062 RV2607000153 RV2607000415 RV2608000418 --outgoing IS2601000016 IS2609000372
  • erp_header.status=FOUND: 해당 기간의 ERP 목록에 전표가 존재합니다. rows의 원본 필드로 날짜·창고·전표 상태 등을 확인합니다. 목록 존재만으로 상세가 0개인 이유까지 확정하지 않습니다.
  • NOT_FOUND_IN_RANGE: 지정한 기간의 목록에 없습니다. 삭제 확정이 아니며 날짜 변경 가능성도 확인합니다. UNVERIFIED는 API 실패나 형식 오류이므로 전표 부재로 판단하지 않습니다.
  • scm_transactions: 기존 수불 건수·저장 수량 합계·품번·출발/도착 창고를 표시합니다. 행은 최대 50개이고 초과 시 truncated=true입니다. 저장 수량 합계는 현재 재고량이 아닙니다.
  • ERP 화면에서 실제로 품목이 있는지와 목록/상세 API의 조회 범위가 같은지 확인한 뒤 빈 전표 처리 기준을 정합니다. 이 결과만으로 빈 상세를 정상 처리하지 않습니다.

추가 진단은 마이그레이션이나 Gunicorn 재시작 없이 코드 업데이트 후 실행할 수 있습니다. 관련 테스트 40건 통과: 기존 35건과 목록/수불 대조, 조회 실패 구분, 날짜 검증, DB 변경 차단 5건.

4. 정상화 후 cron 주기 분리

crontab -e에서 기존 10분마다 실행하는 sync_erp_history 행을 아래 sync_erp_auto 행으로 교체합니다. 02시 변경 감지와 23시 성형/MT 집계는 유지하고, 03시 전체 점검을 추가합니다. 기존 전체 점검 행을 남겨 중복 등록하지 않습니다. 예약 시각은 서버 cron 시간대 기준이며, 각 작업이 겹치면 잠금으로 후속 작업을 건너뜁니다. 첫 적용 후 실행 시간과 전체 점검 성공 기록을 확인합니다.

*/10 * * * * cd /var/www/scm_project && /var/www/scm_project/venv/bin/python -u manage.py sync_erp_auto --days 7 >> /tmp/erp_sync.log 2>&1
0 2 * * * cd /var/www/scm_project && /var/www/scm_project/venv/bin/python -u manage.py detect_past_changes >> /tmp/erp_detect.log 2>&1
0 3 * * * cd /var/www/scm_project && /var/www/scm_project/venv/bin/python -u manage.py sync_erp_history >> /tmp/erp_history.log 2>&1
0 23 * * * cd /var/www/scm_project && /var/www/scm_project/venv/bin/python -u manage.py sync_erp_daily >> /var/log/erp_sync.log 2>&1
