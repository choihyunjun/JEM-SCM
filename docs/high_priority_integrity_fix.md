2026-09-10: SCM / QMS / WMS 높은 우선순위 8개 항목 보완

최고관리자 비밀번호 변경 기능과 사용자 계정 정보는 변경하지 않았다. 이전에 수정한 납품서 중복 등록 방지·납품서별 취소 범위 보호도 유지한다.

| 항목 | 적용 내용 |
|---|---|
| 조회 전용 계정 수정 차단 | QMS 상세 화면의 저장 요청은 해당 수정 권한을 별도로 검사한다. 조회 전용 폼을 비활성화하고 수정·삭제 버튼을 숨긴다. 출하검사, 부적합, 시정조치, 클레임, 협력사평가, ISIR, VOC, 계측기, 품질문서에 적용했다. |
| 해제한 권한 재허용 방지 | SCM·WMS·QMS 서버와 템플릿에서 저장된 개별 권한을 사용한다. 예전 역할 기본값·레거시 플래그로 False를 뒤집지 않는다. 계측기와 품질문서는 각각의 전용 권한을 사용한다. 신규 계정의 역할별 기본 권한 부여는 유지한다. |
| 협력사 자료 범위 | SCM 업체 연결 누락 계정은 접근을 차단하고 발주 엑셀은 소속 업체로 제한한다. QMS의 업체별 자료는 목록·상세·통계·PDF·수정·삭제에서 같은 범위를 적용한다. POST에서 다른 업체로 소유자를 바꾸는 요청도 차단한다. 내부 직원의 권한에 따른 전체 조회는 유지한다. |
| 검사 수량 | 서버에서 양품·불량 각각 0 이상, 입고 수량 이하, 합계 일치를 확인한다. 부분 불량·전량 양품·전량 불량은 유지한다. |
| 동시 판정 | PENDING인 검사에 대한 조건부 UPDATE가 성공한 요청만 재고와 ERP 처리를 진행한다. 재고 차감에도 수량 조건을 적용한다. SQLite에서 두 요청이 같은 대기 상태를 읽는 동시 실행 테스트를 수행했다. |
| 재고 중복 | LOT 날짜 또는 생산 배치가 NULL인 조합에도 유일성 제약을 추가한다. 기존 중복이 있으면 마이그레이션이 먼저 중단되며 임의 합산·삭제하지 않는다. 현재 작업 DB에는 중복이 없었다. |
| 배치·발주 연결 | 입고 이력에 원본 납품서 품목 FK를 추가한다. 검사 이동과 취소는 원본 생산 배치를 유지한다. ERP 입고·단가 재반영은 원본 품목/발주를 사용한다. 과거 연결은 납품서+품번+LOT가 유일할 때만 선택하며 모호하면 중단한다. SCM 입고가 기존 다른 배치의 재고를 합산·삭제하던 부분도 제거했다. |
| ERP 불일치 복구 | 로컬 업무 변경과 ERP 요청을 같은 DB 트랜잭션에 저장하고 커밋 후 전송한다. 등록·삭제 요청, 시도·결과·수동 재처리 이력은 입고 원본 삭제 후에도 유지된다. 타임아웃·불명확한 응답·결과 저장 실패는 확인 필요 상태로 남기며 자동 재전송하지 않는다. |

새 메뉴: **WMS → ERP 입고 연동 관리**. 기존 입고처리 권한으로 접근한다.

- 전송 대기: 아직 전송하지 않은 요청을 전송할 수 있다.
- ERP 확인 필요: ERP 조회로 처리 여부를 확인한다. 신규 등록 요청의 비고에 고유 식별자를 남기고 전표 조회 시 이 식별자와 품목·수량을 대조한다.
- 조회로 확정하지 못하면 자동으로 다시 보내지 않는다. 담당자가 ERP에서 미처리를 확인한 내용을 기록한 뒤 재전송할 수 있다. 이 판단이 잘못되면 ERP에서 중복 처리될 수 있으므로 자동 중복 방지를 완전히 보장하는 방식은 아니다.
- 전송 중 또는 결과가 불확실한 입고의 수정·취소는 결과 확인 전까지 중단한다. 아직 전송하지 않은 요청은 입고 취소와 함께 취소한다. 대기 중 입고를 수정하면 요청 수량도 갱신한다.
- 단가 재반영은 기존 전표 삭제 완료 후 새 전표 등록이 진행되도록 의존 관계를 저장한다. 단가 확인·등록 요청 준비에 실패하면 기존 전표 삭제 요청도 롤백한다.
- 로컬 입고·취소 완료와 ERP 완료는 서로 다른 상태다. 커밋 후 전송 실패 시 로컬 처리 결과와 ERP가 일시적으로 다를 수 있으며, 이 메뉴에서 확인·복구한다.

기본 동작은 커밋 직후 전송이다. 프로세스가 종료되어 남은 대기 건은 메뉴 또는 다음 명령으로 처리한다. 작업 스케줄러에는 아직 등록하지 않았다.

```console
python -B manage.py process_erp_incoming --limit 100
python -B manage.py process_erp_incoming --reconcile --limit 100
```

첫 명령은 실제 ERP 요청을 전송한다. 두 번째 명령은 불명확한 요청을 조회해 확인하며 재전송하지 않는다. 개발 테스트에서는 모든 외부 ERP 호출을 대체했다.

추가 마이그레이션은 `material.0051_receipt_integrity_and_erp_outbox`이다. 이전 수정의 `material.0050`, `orders.0052`에 의존한다. 작업 폴더 DB에 적용했으며, 운영 서버는 별도로 코드와 마이그레이션을 배포해야 한다.

적용 직전 백업: `backups/integrity_apply_20260910_100422_437382/db.sqlite3`. 복사본과 작업 DB 각각에서 마이그레이션을 검증했다. 기존 102개 테이블의 모든 기존 열·행을 해시로 대조했고 동일했다. DB 무결성·외래키 검사도 통과했다. ERP 요청은 생성·전송하지 않았다.

현재 DB의 프로필 ID 7은 과거 발주 조회 플래그가 True이고 현재 `can_scm_order_view`는 False였다. 개별 설정을 존중해 이를 임의로 True로 바꾸지 않았다. 필요하면 기존 권한 관리에서 해당 권한을 켤 수 있다. 계정 비밀번호·소속·저장된 권한 값은 그대로다.

```console
python -B manage.py test orders.test_access_safety qms.test_inspection_safety material.test_receipt_integrity orders.test_delivery_safety material.test_incoming_cancellation qms.test_inspection_links --settings=config.test_settings --noinput
```

55개 테스트 통과. 권한 있는 정상 저장·없는 저장 차단, 업체별 엑셀/상세, 실제 템플릿 렌더링, 잘못된 수량, 두 요청의 동시 판정, 배치·발주 연결, NULL 조합 유일성, 기존 취소 회귀, ERP 커밋 전 전송 금지·롤백·중복 호출·타임아웃·결과 저장 실패·복구·수정·삭제를 포함한다. Python 구문, QMS 템플릿 컴파일, 모델/마이그레이션 차이 없음도 확인했다.

검증 범위: 실제 ERP 서버의 비고 반환 형식·조회 완전성·운영 권한·실제 전표 생성/삭제는 검증하지 않았다. ERP 공급자가 보장하는 멱등 키 API는 확인되지 않아 사용하지 않았으며, 불확실한 건은 조회 또는 담당자 확인으로 처리한다. 테스트가 전체 시스템의 모든 화면·운영 조합을 보증하지는 않는다. 입고 등록·삭제 외의 ERP 생산/재고이동 API는 이번 outbox 대상이 아니다.

기존 신규 DB 설치 문제(material 0045/0046의 updated_by 중복 추가)는 이번 범위에서 변경하지 않았다. 업무 테스트는 `config.test_settings`로 현재 모델에서 격리 DB를 생성하며, 실제 기존 DB 업그레이드는 별도 복사본에서 검증했다. 신규 설치 실패에 임의 `--fake`를 적용하지 않는다.
