# 납품서 중복 등록 및 입고 취소 범위 수정

## 변경된 업무 규칙

- 한 납품서에서 같은 품번 + 생산일 LOT는 한 번만 등록합니다.
  발주번호나 SNP가 달라도 중복으로 처리하며, 화면과 서버 모두 검사합니다.
- 다른 LOT, 다른 품번, 다른 납품서의 동일 품번/LOT 등록은 유지합니다.
- SCM의 '이 품목만' 취소는 선택한 납품서의 그 품목 전체 LOT에 적용합니다.
  '납품서 전체' 취소는 그 납품서의 검사대기 품목까지 포함합니다.
- 수입검사 양품/불량 이동은 원본 입고(source_incoming)에 연결하고,
  발행 라벨은 원본 납품서 품목(delivery_item)에 연결합니다.
- ERP 전표 삭제와 내부 검사 이동 삭제는 동일하게 확정한 기록 ID를 사용합니다.
- ERP 삭제 실패 시 해당 로컬 취소를 중단합니다. 여러 ERP 요청의 원자적
  롤백/재시도 시스템은 이번 변경에 포함하지 않았습니다.

## 기존 데이터

두 새 필드는 NULL을 허용합니다. 마이그레이션은 기존 행을 삭제하거나
추정해서 연결하지 않습니다.

기존 양품 이동은 납품서 + 품번 + LOT + 검사창고 + 이동창고로 원본이
유일한지 검사합니다. 납품서 번호 없는 과거 불량 이동은 동일 검사 대상이
유일할 때만 처리합니다. 과거 라벨도 발주/SNP/수량이 다른 납품서와 겹치면
취소를 중단하고 확인 메시지를 표시합니다.

확인이 필요한 과거 데이터는 실제 납품서/검사 내역과 대조한 뒤
source_incoming 또는 delivery_item 연결을 정정해야 합니다.
다른 납품서의 자료로 추정하여 삭제하거나 전역 검색으로 우회하면 안 됩니다.

## 적용

배포 시 코드와 함께 다음 스키마 변경이 필요합니다.

- orders.0052_labelprintlog_delivery_item
- material.0050_materialtransaction_source_incoming

DB 백업 및 현재 마이그레이션 적용 상태를 확인한 뒤 프로젝트 환경에서
`python manage.py migrate`를 실행합니다. 현재 작업 폴더의 DB는 백업 후
이 두 마이그레이션을 적용했습니다. 별도 운영 서버에는 배포 시 적용해야 합니다.

주의: 기존 material.0045와 0046이 updated_by를 중복 추가하므로 빈 DB에서
전체 마이그레이션을 실행하면 duplicate column 오류가 발생합니다.
이 과거 이력 문제는 이번 두 기능 수정과 별개이며, 무조건 --fake로
넘기지 말고 실제 DB 스키마와 적용 이력을 확인해야 합니다.

## 검증 실행

```text
python -B manage.py test orders.test_delivery_safety material.test_incoming_cancellation qms.test_inspection_links --settings=config.test_settings
```

config.test_settings는 메모리 DB, 메모리 파일 저장소와 메일함을 사용하고
ERP를 비활성화합니다. 기능 테스트는 현재 모델로 테이블을 구성하므로
전체 마이그레이션 이력 검증을 대신하지 않습니다.

새 마이그레이션 두 개는 별도 메모리 DB의 변경 전 스키마에 적용하여
기존 샘플 행과 수량 보존을 확인했습니다. 실제 ERP 통신 및 운영 DB는
변경하지 않았습니다.
